CTFshow pwn142：从堆越界小实验到 off-by-one、堆块重叠与 GOT 劫持

这篇记录从我们一起做的堆越界小实验开始，再把观察到的现象带到 CTFshow pwn142。内容包括 malloc/free 的 chunk 布局、越界写如何改到相邻 chunk 的 size、释放后再分配如何形成堆块重叠，以及如何通过 free@GOT 泄露 libc 并把它改成 system。
我一开始卡住的地方主要有这些：为什么两个用户指针相差 0x20；0x21 和 0x41 分别表示什么；断点应该打在 read 前还是后；怎样确认 b 的 size 被改了；为什么 c == b 之后写 c 会覆盖 guard；以及 pwn142 里为什么每个 note 有两次 malloc、edit(1, p64(system_addr)) 又为什么会写到 GOT。下面按我们实际调试的顺序来。

先补齐这题需要的堆基础

用户请求大小不等于 chunk 总大小

malloc(0x18) 的 0x18 是程序请求的用户数据长度，不是从 chunk 头部开始计算的总长度。在我这次调试的 64 位 glibc 环境中，malloc(0x18) 和 malloc(0x10) 都对应 size 字段为 0x21 的 chunk：

低三位里包含标志位；这里最低位 1 表示 PREV_INUSE。因此 chunk 的大小部分是 0x20。这正是为什么请求 0x18 和 0x10，相邻用户指针常常仍相差 0x20。
注意：具体行为受架构、glibc 版本和请求大小影响。本文的地址和结果是本题、当前调试环境中的实测，不要把某个地址或版本细节机械套到所有题目。

free 不会把指针变量自动清零

free(ptr) 把对应 chunk 交还给分配器；它不会替程序把保存该地址的变量自动设为 NULL。而且 chunk 被释放后，分配器会把一部分原用户区改作空闲链表元数据。所以释放前后看到用户区内容变化是正常的，不代表原数据被“整块擦除”。
本题后面会依赖释放后的 chunk 被不同大小的申请重新取回；判断是否重用，必须对照地址，不能只凭变量名或 note 索引猜。

我这题里真正弄懂的几个问题

为什么 create 有两次 malloc？

因为每个 note 由控制结构和内容区组成。控制结构固定 malloc(0x10)，内容区再按用户输入大小 malloc(size)。

为什么两个控制块地址相差 0x40？

两次 create 之间不只分配控制块 0 和控制块 1；控制块 0 与控制块 1 中间还分配了内容块 0。当前环境下这几个申请各占一个 0x20 chunk，所以控制块之间跨了两个 chunk。

0x41 为什么能让后面的分配变大？

chunk size 字段的低位含标志；0x41 的大小部分是 0x40，最低位 1 是标志。分配器随后会按 0x40 大小处理这个控制块 chunk。

p64(free_got) 是不是已经泄露了 free？

不是。p64(free_got) 只把 GOT 槽位的地址写进控制结构。show(1) 通过这个指针读取并打印 GOT 槽位中的内容，才泄露出 libc 的 free 地址。

为什么 edit(1, p64(system_addr)) 会写 GOT？

因为重叠写先把 note 1 控制结构的 content 指针改成了 free@GOT。edit 按这个指针写，所以 8 字节的 system 地址落在 GOT 槽位。

为什么最后删 note 0 能拿 shell？

note 0 的内容是 /bin/sh\x00；free@GOT 已经指向 system，删除 note 0 时原本的 free(content) 变成 system(content)。

总结

pwn142 的核心不是“堆上随便写一个地址”，而是利用一个字节的越界改变相邻控制块 chunk 的大小，再让分配器把原本不同用途、不同尺寸的块按新的尺寸复用。重叠之后，我们改的是 note 控制结构中的 content 指针；show 让这个指针变成读原语，edit 让同一个指针变成写原语，最终完成 free@GOT → system。
我这次最有效的调试方法，是把每一轮分配都按真实地址标出来：控制块地址、内容块地址、chunk 头部、size 字段和重叠区域分别确认。只看 heaparray[0]、heaparray[1] 这些索引容易把“note 编号”和“堆地址”混为一谈；把地址关系画出来后，为什么 0x18、0x10、0x30 和 0x41 这样组合就清楚了。
