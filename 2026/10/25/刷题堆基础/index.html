题目一：VCS First UAF 与 tcache poisoning 劫持 exit@GOT

这篇记录我们最近练习的 vcs_first。目标是通过释放后仍可编辑的堆块，改写 tcache 链表中的 next，让一次后续分配返回 exit@GOT，再把 GOT 表项改成题目里的 winner，最后通过非法索引触发 exit()。
最开始我把 tcache -> chunk0 -> exit@GOT 理解成“exit@GOT 里面已经写了什么”。其实这条链描述的是分配器下一步会把哪个地址当作空闲 chunk；exit@GOT 是一个地址，只有后续把它作为分配结果使用并编辑时，才会向该地址写入数据。下面按利用实际发生的顺序拆开。

附件 vcs_firest

先从源码确认程序对象和漏洞

题目反编译里的 create 核心逻辑是

每次 create(index) 只做一次 malloc(0x50)，然后把返回的堆地址放进 itemList[index]。这里不是“一个 note 结构再 malloc 一块内容”的两次分配；这是一个固定大小的堆对象。

delete 会释放对应堆块，但没有把 itemList[index] 清成 NULL。因此释放后数组里还留着旧地址，程序仍可能通过它访问已经释放的内存，这就是 UAF（Use-After-Free，释放后使用）的基础。

edit 会通过索引取出 itemList[index]，再把输入复制到这个地址。对象释放后指针仍在，所以可以借 edit 改写 tcache 空闲块用户区开头的链表指针。

view 的关键逻辑是

它把堆地址当 C 字符串打印。若对应 chunk 已释放，打印结果可能暴露分配器写在用户区里的 tcache 元数据；不过 puts 遇到 \0 就停止，所以这是受字符串终止符影响的泄露，不是固定长度的任意读。

利用脚本的结构

下面是利用步骤的骨架。提示字符串、view 输出解析和 edit 输入方式需要按本地二进制核实；尤其是是否启用 safe-linking、view 能否泄露出完整所需 key、strcpy 是否只能做部分覆盖。

这段是帮助理解流程的骨架，不保证可以不经调整直接跨 libc 运行。特别注意：

  1. view(1) 必须确实读到释放后的 chunk1，而不是菜单提示或空字符串。
  2. 用 chunk1 的 key 去编码 chunk0 的 next，要求两者的用户地址落在同一个 4KB 页面。
  3. edit 若经过 strcpy，嵌入 NUL 会截断复制；需要确认题目的 GOT 覆盖方式是否利用了部分覆盖。
  4. 本机 glibc 若与附件/远程不一致，tcache 的校验和编码规则也可能不一致。

这次最重要的理解

我最后整理出的利用链是：先让 tcache 形成 chunk0 -> chunk1 -> NULL；再用 UAF 改写 chunk0 的 next，使下一跳成为 exit@GOT；之后两次 create 分别取出 chunk0 和伪造的 GOT 节点；索引 3 因而指向 exit@GOT，通过 edit(3, ...) 改写这个表项；最后 create(-1) 触发越界分支调用 exit()，程序控制流被转到 winner。
