因此不能在 delete 后直接用 edit(index) 访问已释放块，因为 heaparray 中对应槽已清零。本题的做法是：保留相邻的 chunk 1 为已分配状态，从 chunk 1 越界写，覆盖旁边已释放的 chunk 2 元数据。

read_input：为什么 payload 输入方式很重要

read_input 的反汇编显示它只调用一次 read：

它不会循环读取直到凑满 length，也不会自动补 NUL。也就是说：

  • create 的输入内容比申请大小短时，read 可以只读到当前已经送来的字节。
  • edit 的二进制 payload 如果正好是 0x40 字节，应该用 p.send(payload)，不要用 p.sendline(payload)。
  • p.sendline 会多送一个换行；read 最多取 0x40 字节时，那个换行可能留在输入流里，干扰下一次菜单读取。

为什么选 0x500、0x20、0x500、0x20

我按这个顺序申请：

选择 0x500 的大块，是为了让它进入 unsorted bin。glibc 2.27 虽然有 tcache，但 0x500 这个请求对应的 chunk size 超过 tcache 管理范围。0x80 则会落在 tcache 管理范围内，不能仅因为换成 2.27 就认定它进入 unsorted bin。
在 amd64 下，GDB 中看到的 chunk size 字段还包含低位标志。请求 0x500 对应 chunk 总大小 0x510，因此通常看到 0x511；请求 0x20 对应总大小 0x30，因此通常看到 0x31。

prev_size 为什么填 0

这是 chunk 2 头部的前一个 chunk 大小字段。size 写成 0x511，最低位 PREV_INUSE 为 1，表示前一个 chunk 仍视为 in-use；这种状态下 allocator 不依赖 prev_size 做向前合并。这里填 0 是 payload 对字段的明确覆盖值。

size 为什么写 0x511

chunk 2 原申请大小是 0x500。glibc 对齐后 chunk 总大小为 0x510；size 字段还带 PREV_INUSE 标志，所以写入 0x511。这个值也和释放前 GDB 中观察到的 size 一致。

fd 为什么写 0

payload 把 chunk 2 自己的 fd 字段写成 0。fd 的这个值不是 magic，也不是写入目标地址；本次写入目标由 bk 决定。0 是该利用 payload 对 fd 字段的设置，是否可用要以当前 libc 的 allocator 检查和实际运行结果为准。

修正后的 pwntools 脚本

read_input 只调用一次 read。创建内容短于申请大小时，sendline 发送的换行也会被这次 read 一并读走；0x40 字节的二进制编辑 payload 则必须用 send，避免额外换行残留在菜单输入里。
